# 古兰经祷告 App 技术方案

- 日期：2026-05-09
- 项目：古兰经祷告 App 产品线
- 目标：支撑 4 个独立 app（印尼/中东 × 男女）
- 技术策略：一套可配置内核 + 四套品牌/内容/推送配置
- 核心特点：重推送、强内容调度、离线兜底、轻量高频

## 一、技术目标

这套技术方案不是为了支撑一个“大而全伊斯兰超级应用”，而是为了稳定支撑一个 **每日经文 -> 祷告 -> 完成** 的高频轻闭环。

技术上必须优先满足 4 个目标：

1. **准时触达**：每天把正确的内容在正确时间送达用户
2. **秒开可读**：即使弱网或无网，用户点开也能看到当天内容
3. **可配置复制**：同一套代码可以快速分化成 4 个 app
4. **低运营摩擦**：内容、推送文案、广告规则可热更新，不必每次发版

## 二、总体架构

整体建议拆成 8 个模块：

1. App Shell 模块
2. 配置中心模块
3. 内容包与内容调度模块
4. 远程推送模块
5. 本地推送兜底模块
6. 离线缓存与回退模块
7. 广告规则模块
8. 数据埋点与实验模块

### 总体关系

- `App Shell` 负责 UI、导航、基础状态管理
- `配置中心` 决定当前 app 属于哪个 market/gender 配置
- `内容调度模块` 决定今天展示哪条 ayah 与哪段 reflection
- `远程推送模块` 负责线上触达
- `本地推送兜底模块` 负责没有线上触达时仍能提醒
- `离线缓存模块` 确保今天内容、本周内容和默认兜底内容始终可用
- `广告规则模块` 决定哪些页面可展示广告、哪些页面严格禁投
- `埋点模块` 负责分析推送效果、阅读转化和祷告完成率

## 三、模块拆分

## 1. App Shell 模块

### 职责
- 承载 4 个 app 的统一 UI 外壳
- 负责页面导航、主题切换、本地设置、基础存储
- 将各业务模块按统一接口接入

### 页面结构
- Today 首页
- Prayer 页面
- Completion 页面
- History 页面
- Saved 页面
- Settings 页面

### 关键要求
- 主题、文案、默认语言必须配置化
- 不把 market/gender 逻辑散落在页面里
- 页面层只消费统一 ViewModel，不直接写复杂业务判断

### 技术建议
- 单仓工程，多 app flavor / target
- 统一 design tokens：颜色、字体、圆角、插画资源包
- 统一导航骨架，按配置切首页文案和样式

## 2. 配置中心模块

### 职责
- 决定某个 app 的品牌、语言、内容池、推送文案包、广告规则包
- 作为“一套内核 + 四套壳”的核心枢纽

### 配置维度
- `app_id`
- `market`：`ID` / `ME`
- `gender`：`male` / `female`
- `default_language`
- `rtl_enabled`
- `theme_pack`
- `content_pack`
- `push_pack`
- `women_mode_enabled`
- `ad_ruleset`
- `feature_flags`

### 配置来源
- 安装包内置默认配置
- 启动后从远端拉取增量配置
- 本地持久化最后一版有效配置

### 回退策略
- 远端配置失败 -> 使用上次成功配置
- 首次安装且远端失败 -> 使用包内默认配置
- 配置版本非法 -> 回退到上一个稳定版本

## 3. 内容包与内容调度模块

这是整套系统最核心的模块之一。

### 职责
- 管理 4 个 app 对应的 ayah / translation / reflection / prayer prompt 内容
- 决定用户当天应该看到什么内容
- 为推送、本地提醒、首页、祷告页、完成页统一提供内容

### 内容层级

#### A. 通用内容源
- Quran ayah 原文
- 基础译文
- 基础主题标签

#### B. 市场内容层
- 印尼版文案改写
- 中东版文案改写
- Arabic-first 内容组织

#### C. 性别内容层
- 男性主题 reflection
- 女性主题 reflection
- 女性经期友好内容包

### 内容数据模型
建议单条内容结构包含：
- `content_id`
- `date_key`
- `market`
- `gender`
- `theme`
- `ayah_reference`
- `arabic_text`
- `translation_text`
- `reflection_text`
- `prayer_prompt`
- `notification_title`
- `notification_body`
- `fallback_rank`
- `menstruation_safe`
- `ramadan_only`
- `language_bundle_version`

### 调度规则

#### 日级调度
每天只生成 1 条主内容：
- 今日 ayah
- 今日 reflection
- 今日 prayer prompt
- 今日推送文案

#### 女性模式调度
若用户开启或触发生理期模式：
- 不推送强调“完成祷告”压力的文案
- 首页可切换为 dua / reflection 优先
- Completion 概念替换为“今日陪伴已完成”或类似 softer 文案

#### 节日调度
- Ramadan / Eid 期间切换专题内容池
- 节日优先级高于普通日常内容

## 4. 远程推送模块

这是一号增长模块。

### 职责
- 通过线上 push 将当日内容触达用户
- 支持不同市场、性别、语言、时区的分发
- 支持不同用户的提醒时间偏好

### 推送类型

#### A. 每日主推送
- 每天 1 条核心触达
- 打开后直达 Today 页面

#### B. 女性版双节点推送
- 可选 morning reflection
- 可选 evening calm reminder

#### C. 节日/专题推送
- Ramadan / Eid 专题提醒
- 频率严格受限

### 远程推送载荷建议
- `notification_id`
- `app_id`
- `content_id`
- `campaign_type`
- `open_target=today`
- `deep_link`
- `scheduled_at`
- `locale`
- `fallback_allowed=true`

### 推送分发逻辑

#### 推荐做法
- 服务端按用户本地时区计算发送时间
- 按 app_id、market、gender、language 分组
- 支持用户自定义提醒时间
- 未设置时间时用默认时段

#### 默认时段建议
- 印尼男性：清晨或上班前
- 印尼女性：清晨 / 晚间二选一或双节点
- 中东男性：清晨优先
- 中东女性：更温和的白天/晚间时段

### 失败场景
- 推送 token 失效
- 系统通知权限关闭
- 服务端调度失败
- 第三方推送平台失败

这些都不能让产品失去提醒能力，因此必须接本地推送兜底。

## 5. 本地推送兜底模块

这是远程推送失败时的二号保障。

### 职责
- 在本地预排未来若干天提醒
- 当远程推送未到达或网络不可用时，仍能按时提醒
- 与本地缓存内容联动，保证提醒点开后能看到内容

### 基本策略
- 首次完成 onboarding 后，立即在本地预排 7 天通知
- 每次应用启动、前台恢复、静默刷新成功后，重建未来 7-14 天本地通知
- 若远程推送已经在当天成功触发，本地通知可自动取消或降级

### 本地通知生成规则
本地通知不直接写死文本，而从本地内容缓存中生成：
- 读取未来 N 天内容包
- 为每一天生成本地文案
- 按用户设定时间注册通知

### 去重策略
需要避免远程 + 本地双响：
- 当远程推送成功投递并记录回执后，取消当日本地通知
- 若无法获得可靠投递回执，则以“应用打开即视为已触达”作为兜底去重信号
- 本地通知在触发前 15-30 分钟检查是否已完成去重标记

### 降级场景
- 没网但已有缓存内容 -> 本地通知正常发
- 没网且缓存内容缺失 -> 发极简默认提醒文案
- 用户关闭线上通知权限 -> 依赖系统允许范围内的本地通知；若系统通知总权限关闭，则只能在下次 app 打开时补提醒

## 6. 离线缓存与回退模块

这套产品必须按“弱网可用、离线可读”设计。

### 职责
- 缓存内容、配置、最近状态
- 保证无网情况下 Today 仍可读
- 支撑本地通知与离线打开场景

### 缓存层级

#### A. 首日缓存
- 今天内容必须强制本地持久化

#### B. 短期缓存
- 未来 7 天内容
- 过去 7 天内容

#### C. 中期缓存
- 未来 30 天主题索引与最小内容包

#### D. 安装包内默认内容
- 至少内置 14 天兜底内容
- 首次安装无网时也可立刻使用

### 缓存对象
- 内容包
- 配置包
- 推送模板包
- 广告规则包
- 用户设置
- streak / completion 状态

### 离线打开 Today 页逻辑
优先级：
1. 今日远端最新内容
2. 今日本地缓存内容
3. 今日默认兜底内容
4. 若日期映射失败，展示通用静态 devotional fallback

### 内容更新策略
- 冷启动时检查内容版本
- 每日首次打开时检查内容版本
- 后台唤醒时静默拉取最新内容
- Wi-Fi 下可预拉未来 30 天内容包
- 蜂窝网络下优先只拉未来 7 天增量

## 7. 内容更新模块

这是推送系统的配套模块。

### 职责
- 热更新 ayah 解释、reflection、push 文案、节日专题包
- 不依赖发版完成日常运营

### 更新粒度
- 配置更新
- 内容更新
- 推送模板更新
- 广告规则更新
- 节日专题更新

### 更新方式
建议使用版本号 + 增量包：
- `config_version`
- `content_version`
- `push_pack_version`
- `ad_ruleset_version`

### 更新流程
1. App 启动读取本地版本
2. 请求远端版本摘要
3. 若有更新，按模块下载增量包
4. 下载完成后做数据校验
5. 校验通过后原子替换
6. 重建本地未来通知

### 安全要求
- 增量包必须有签名或校验摘要
- 下载失败不能污染现有稳定数据
- 内容上线需支持快速回滚

## 8. 广告规则模块

### 职责
- 统一控制哪些页面展示广告，哪些页面绝不展示
- 支持不同市场与女性模式的广告策略差异

### 规则结构
- `placement_id`
- `page`
- `enabled`
- `market`
- `gender`
- `frequency_cap`
- `cooldown_seconds`
- `blocked_in_women_mode`

### 核心规则
- Prayer 页面永不投放
- Quran 正文核心阅读区域永不插入广告
- Completion 页面广告需在祝福/反思内容之后
- 经期模式相关提示页默认禁广告

## 9. 数据埋点与实验模块

### 职责
- 衡量推送是否带来打开、阅读、祷告、完成
- 发现不同 app 的最佳提醒时间、文案、页面节奏

### 核心事件
- `push_remote_sent`
- `push_remote_open`
- `push_local_scheduled`
- `push_local_fired`
- `today_content_loaded_remote`
- `today_content_loaded_cache`
- `today_content_loaded_fallback`
- `prayer_start`
- `prayer_complete`
- `completion_page_view`
- `ad_impression`
- `ad_click`

### 关键指标
- 远程推送送达率
- 远程推送打开率
- 本地推送触发率
- Today 页面内容来源占比（远端/缓存/兜底）
- Prayer completion rate
- 次日留存 / 7 日留存

### 可做实验
- 推送时间 A/B
- 推送语气 A/B
- 完成页 reflection 形式 A/B
- 女性双节点提醒是否提升留存

## 四、按模块的数据流

## 1. 首次安装
- 读取安装包默认配置与默认内容
- 用户完成 onboarding，选择语言与提醒时间
- 注册远程推送 token
- 本地预排未来 7 天通知
- 下载对应 app 的远端配置与内容增量

## 2. 每日运行
- 服务端按计划发送远程推送
- 本地仍保留当日兜底通知
- 用户点开后加载 Today 内容
- 优先远端数据，其次本地缓存，再次默认兜底
- 用户进入 Prayer 并完成
- 记录 completion，并更新 streak

## 3. 后台更新
- App 启动或唤醒时检查版本
- 若内容/推送文案更新，下载增量
- 下载成功后刷新本地内容索引
- 重建未来本地通知

### Phase 1：核心闭环

## 六、我对这套技术方案的判断

### 结论 1
这是一个 **内容调度系统 + 推送系统驱动** 的 app，不是普通静态内容 app。

### 结论 2
真正的技术护城河不在 UI，而在：
- 内容版本系统
- 远程/本地推送协同
- 离线回退稳定性
- 4 app 共内核的配置化能力

### 结论 3
如果要先做 MVP，最重要的是把这 3 件事一次做对：
1. Today 内容总能打开
2. 推送总能在合理时间触达
3. 离线状态总有内容可读

只要这三点稳定，后面的品牌和商业化才有意义。
